04 — Database Design
Purpose

This document defines the complete relational database design for SynapseHR.

The database serves as the single source of truth for all persistent application data.

The design emphasizes:

Data integrity
Normalization
Scalability
Performance
Auditability
Maintainability
Database Engine

PostgreSQL 16+

Reasons:

ACID compliance
Strong relational modeling
JSON support
Full-text search
Excellent indexing
Enterprise reliability
Naming Conventions
Tables

Use plural snake_case.

Examples

employees
departments
leave_requests
workflow_logs
Columns

Use snake_case.

Examples

employee_id
created_at
updated_at
manager_id
Primary Keys

Every table uses

id UUID PRIMARY KEY

UUIDs should be generated by the application.

Timestamps

Every table must include

created_at
updated_at

Type

TIMESTAMP WITH TIME ZONE
Soft Deletes

Tables supporting deletion should include

deleted_at

instead of permanent deletion.

Data Integrity Rules

Every employee

Must belong to one department.

Every department

Must belong to one organization.

Every leave request

Must belong to one employee.

Every workflow

Must belong to one employee.

Every message

Must belong to one conversation.

Migration Strategy

Use Alembic.

Rules

Never edit existing migrations.
Create a new migration for every schema change.
Test every migration on a clean database.
Support rollback where possible.
Database Security
Parameterized queries only.
No raw SQL unless justified.
Least-privilege database user.
Encrypted connections in production.
Regular backups.
Audit logging enabled.
Definition of Database Completion

The database layer is considered complete when:

All entities are modeled.
Relationships are enforced.
Constraints protect data integrity.
Indexes support expected query patterns.
Migrations are version-controlled.
Audit logging is available.
Future modules can be added without breaking existing tables.
