# 06.2 — Service Layer Architecture

# Purpose

The Service Layer is the central orchestration layer of the SynapseHR backend.

It contains all business rules, coordinates transactions, invokes repositories, communicates with AI agents when necessary, and ensures that every business operation is executed consistently.

No business logic shall exist outside this layer.

---

# Responsibilities

The Service Layer is responsible for:

- Business rule enforcement
- Validation beyond schema validation
- Coordinating repositories
- Transaction boundaries
- Invoking AI workflows
- Calling external integrations
- Domain event generation
- Permission checks
- Audit logging triggers

---

# Responsibilities It Must NOT Have

The Service Layer must never:

- Handle HTTP requests
- Return HTTP responses
- Perform raw SQL
- Parse JWT tokens
- Render UI
- Access browser state

---

# Business Rules

Every business rule belongs here.

Examples

Leave balance validation

Policy enforcement

Document eligibility

---

# Transactions

Multi-step operations must execute within a single transaction.

Example

Approve Leave

↓

Validate Request

↓

Update Leave Balance

↓

Update Leave Status

↓

Create Notification

↓

Create Audit Log

↓

Commit

If any step fails

↓

Rollback Entire Transaction

---

# Service Communication

Services communicate through interfaces.

Never instantiate services manually.

Avoid circular dependencies.

Prefer orchestration over tightly coupled logic.

---

# AI Integration

Services never call LLM providers directly.

Instead

Service

↓

Planner Service

↓

Agent

↓

Tool

↓

Repository

This allows AI providers to be replaced without changing business logic.

---

# Validation Strategy

Validation occurs in multiple layers.

Pydantic

↓

Business Rules

↓

Repository Constraints

# Error Handling

Services raise domain-specific exceptions.

Examples

EmployeeNotFound

LeaveBalanceExceeded

PolicyViolation

DuplicateEmployee

UnauthorizedOperation

API layers convert these into HTTP responses.

---

# Naming Conventions

Every service class ends with

Service

Examples

EmployeeService

LeaveService

ChatService

---

# Extensibility

New business modules should require only

- New Service
- New Repository
- New API Router

Existing services should remain unchanged whenever possible.

---

# Definition of Completion

The Service Layer is complete when

- Business logic exists only here.
- Repositories remain persistence-only.
- AI interactions are delegated.
- Transactions are correctly bounded.
- Services are independently testable.
