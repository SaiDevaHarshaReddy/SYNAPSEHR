# 06.3 — Repository Layer Architecture

# Purpose

The Repository Layer provides an abstraction over data persistence.

It isolates business logic from database implementation details and ensures that the remainder of the application remains independent of SQLAlchemy and PostgreSQL.

Repositories are responsible only for data access.

---

# Responsibilities

Repositories shall

- Query data
- Insert data
- Update data
- Delete data
- Manage persistence
- Execute optimized queries

Repositories shall never

- Implement business rules
- Execute workflows
- Invoke AI
- Perform authorization
- Generate notifications

---

Each aggregate owns one repository.

---

# Repository Pattern

Repositories expose domain-oriented methods instead of generic CRUD whenever possible.

Good

find_employee_by_email()

find_pending_leave_requests()

get_department_manager()

find_active_policies()

Avoid

execute_query()

run_sql()

generic_select()

---

# Database Interaction

Repositories communicate exclusively with

SQLAlchemy ORM

↓

PostgreSQL

No raw SQL unless performance requirements justify it.

---

# Transactions

Repositories do not own transactions.

Transaction boundaries belong to the Service Layer.

Repositories participate in transactions initiated by services.

---

# Return Types

Repositories return

Domain Models

Optional Domain Models

Collections

Never return HTTP responses.

Never return JSON.

---

# Query Optimization

Repositories should

Use indexes

Avoid N+1 queries

Use eager loading where appropriate

Paginate large datasets

Batch operations when possible

---

# Soft Deletes

Repositories must respect soft deletion.

Deleted records are excluded unless explicitly requested.

---

# Error Handling

Database-specific exceptions remain inside repositories.

Repositories convert them into repository exceptions where appropriate.

Business exceptions are never raised here.

---

# Testing

Repositories are tested against a real PostgreSQL instance or dedicated test database.

Tests include

CRUD

Constraints

Relationships

Indexes

Transactions

Pagination

---

# Dependency Rules

Repositories may depend on

Database Session

ORM Models

Configuration

Repositories may never depend on

API

Services

Agents

Frontend

---

# Naming Convention

Every repository ends with

Repository

Examples

EmployeeRepository

LeaveRepository

WorkflowRepository

---

# Future Compatibility

The Repository Layer should remain valid if the storage engine changes.

Future possibilities

PostgreSQL

CockroachDB

Amazon Aurora

Distributed SQL

Business logic should remain unaffected by such changes.

---

# Definition of Completion

The Repository Layer is complete when

- Every aggregate has a dedicated repository.
- No business logic exists inside repositories.
- Query performance is optimized.
- Transaction ownership remains outside repositories.
- Storage implementation is isolated from the remainder of the application.
