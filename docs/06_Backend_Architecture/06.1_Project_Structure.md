06.1 — Backend Project Structure
Purpose

This document defines the structural organization of the backend codebase for SynapseHR.

The objective is to establish a modular, maintainable, and scalable project layout that clearly separates responsibilities and minimizes coupling between components. Every backend module must adhere to this structure.

The backend is implemented as a modular monolith using FastAPI. Although deployed as a single application, each functional area is designed to evolve independently and can later be extracted into separate services if necessary.

Architectural Philosophy

The backend is designed around four principles.

Separation of Concerns

Each module should have exactly one primary responsibility.

Examples:

API modules expose HTTP endpoints.
Services contain business logic.
Repositories interact with the database.
Agents orchestrate AI workflows.

Responsibilities must never overlap.

Dependency Direction

Dependencies always move inward.

Presentation Layer

↓

Application Layer

↓

Domain Layer

↓

Infrastructure Layer

No lower layer should depend on a higher layer.

Explicit Boundaries

Every folder represents a logical subsystem.

No module may access another subsystem's internal implementation directly.

Interaction occurs through services or interfaces.

Future Scalability

The folder structure must remain valid if the application grows from

10 employees
to 100,000 employees

without major restructuring.

Every production module belongs somewhere inside this directory.

main.py

Responsibilities

Create FastAPI application
Register middleware
Register exception handlers
Register routers
Configure startup events
Configure shutdown events

This file should contain application bootstrap code only.

Business logic must never appear here.

api/

Purpose

Expose HTTP endpoints.

The API layer converts HTTP requests into application service calls.

Responsibilities:

Receive requests
Validate request models
Authenticate users
Authorize users
Return HTTP responses

The API layer must never:

Execute SQL
Access repositories directly
Call AI models directly
Contain business logic

Contains SQLAlchemy ORM models.

Each model represents one database table.

Example

models/

employee.py

department.py

notification.py

Models contain

Relationships
Constraints

Models must never contain business logic.

schemas/

Contains Pydantic models.

Purpose

Separate external API contracts from internal database models.

Examples

EmployeeCreate

EmployeeUpdate

EmployeeResponse

LeaveRequestCreate

LeaveRequestResponse

Every request and response uses schemas.

Never expose ORM models directly.

repositories/

The repository layer abstracts database access.

Responsibilities

CRUD operations
Query optimization
Transaction helpers

Repositories never:

Call APIs
Execute workflows
Call AI
Perform authorization

One repository should manage one aggregate.

Example

EmployeeRepository

LeaveRepository

UserRepository
services/

This is the heart of the application.

Services contain business logic.

Examples

EmployeeService

LeaveService

WorkflowService

ChatService

AnalyticsService

NotificationService

Responsibilities

Validation
Coordination
Transactions
Workflow execution

Services communicate with repositories.

Repositories never communicate with services.

agents/

Contains autonomous AI agents.

The backend treats AI as an independent subsystem.

Example

PlannerAgent

PolicyAgent

LeaveAgent

DocumentAgent

ApprovalAgent

Each agent owns one responsibility.

tools/

Tools expose deterministic operations to AI agents.

Examples

check_leave_balance()

create_leave_request()

generate_document()

retrieve_policy()

send_email()

Agents invoke tools.

Tools invoke services.

Tools never communicate with the database directly.

workflows/

Contains business workflow definitions.

Examples

LeaveWorkflow

PromotionWorkflow

OnboardingWorkflow

ExitWorkflow

A workflow coordinates multiple services and agents.

middleware/

Cross-cutting concerns belong here.

Examples

Authentication

Request Logging

Request ID

Rate Limiting

CORS

Performance Monitoring

Middleware must remain stateless whenever possible.

utils/

Contains reusable helper utilities.

Examples

Date formatting
File helpers
Encryption utilities
Parsing utilities

Utilities should not depend on business modules.

tests/

Testing mirrors production structure.

tests/

api/

services/

repositories/

agents/

integration/

e2e/

Every production module should have a corresponding test module.

Module Independence

Each module should satisfy the following:

Can be tested independently.
Can be understood independently.
Has a single responsibility.
Minimizes external dependencies.
Extensibility

Future modules should integrate without modifying existing architecture.

Examples

Payroll
Attendance
Recruitment
Asset Management
Performance Reviews

Adding these modules should require only new folders and service registrations, not architectural changes.

Definition of Completion

The backend project structure is complete when:

Every responsibility has a dedicated module.
Dependency rules are enforced.
Folder organization remains consistent.
New features can be added without restructuring.
AI components remain isolated from infrastructure concerns.
